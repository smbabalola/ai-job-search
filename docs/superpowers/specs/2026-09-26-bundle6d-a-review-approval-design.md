# Bundle 6D-A — Review & Approval: Design Specification

**Status:** draft for review (2026-09-26). No production code is written against this document until it is approved.
**Branch:** `bundle6/6d-a-review-approval-design`, from verified `master@fc316eec0050b6ae9deada2981089cbac1532adb` (Bundle 6C merged).
**Companion plan:** `docs/superpowers/plans/2026-09-26-bundle6d-a-review-approval.md` (phased, draft).

## 1. Purpose and the core invariant

The default JobSearch workflow is now:

```text
PREPARE  →  REVIEW  →  FILL  →  SUBMIT
(6C)        (6D-A)     (6D-B)    (6E-A; 6E-B optional)
```

6D-A defines the **human review and approval contract** that every later automation step relies on. Everything else in Bundle 6D/6E consumes this contract; nothing may bypass it.

> **Core invariant (I-1): No action beyond what the user actually reviewed may inherit the user's approval.**

Concretely, an approval is a record of *one exact application*, identified by a content hash over everything the user was shown (§9). The approval stays valid only while the current state still recomputes to exactly the same hash. There's no "mostly the same" and no manual refresh. Anything the user didn't see is by definition not approved.

Supporting invariants:

- **I-2 Approval is not authority.** An approval records the user's consent to the *content and target*. Authority (capability, standing policy, budgets, limits, kill switch, pause) stays with 6B and is evaluated separately and freshly. Both are required for FILL. Neither alone is enough.
- **I-3 Approval for filling never grants submission.** 6D approvals cannot represent submission consent (§12). Submission authority is a separate, one-time, per-application record introduced in 6E-A.
- **I-4 The user owns what they edited.** User-supplied or user-edited content is never silently replaced, merged or regenerated by the AI (§7.4).
- **I-5 One application, one approval record.** Bulk actions create one independent approval record per application (§10).
- **I-6 History is append-only.** Every approval, edit, invalidation, revocation and re-approval is an immutable event (§13). Current state is derived by `seq`, never by timestamp.

## 2. Scope and bundle separation

| Bundle | Owns | Explicitly does not |
|---|---|---|
| **6D-A — Review & Approval** (this spec) | Prepared Applications review UI; document preview/replace/edit; planned-answer review and editing; claim provenance; warnings; the approval record and its binding; invalidation; bulk approval; review deltas (intake contract); audit history; the approval-≠-submission boundary | Open employer sites, fill forms, drive a browser, click anything, submit |
| **6D-B — FILL** | Filling an *approved* application on the employer site behind a technical submit firewall; registering newly discovered fields as review deltas (§11) | Activate the employer's final submit control; fill anything outside the approved binding |
| **6E-A — User-authorized SUBMIT** | "Submit application": a one-time, per-application submission authorization bound to the same binding hash plus policy/control version; the pre-click transaction | Submit without that authorization |
| **6E-B — Optional autonomous SUBMIT** | An explicitly enabled higher-trust mode (off by default, deliberate activation, strong warning) | Become the default; weaken 6B limits, pause, kill switch or audit |

Operating modes (account setting, introduced for real in 6E-B, named here so the contract is stable): **Prepare only** → **Review before submit** (default) → **Autonomous submit**. 6D-A implements the review surface and approval records. Modes other than the default are not selectable in 6D.

**Non-goals for 6D-A:**
- browser automation or extension changes;
- fill manifests produced from live pages;
- PDF conversion (Decision D2);
- an in-app word processor;
- changes to 6C scheduling behaviour (§15);
- any path to `applied`.

## 3. Verified baseline (`master@fc316ee`)

What 6D-A builds on, unchanged:

- **Final documents (CV Quality v2).** Documents are immutable `application_document_versions` (`origin` `ai_generated` | `user_uploaded`, `sha256`, `byte_length`, content-addressed blob store). A single `application_document_selections` pointer per kind carries an explicit `revision`, and `reusable_application_documents` holds documents saved for reuse. v2 Gate 4 (`_confirm_application_pack_v2`) binds exact selection revisions into an immutable `application-pack.v2` artifact. Its `final_documents[kind]` carries the version id, sha256, byte length, origin and filename. The governing principle is *"AI creates the documents. The human owns the final documents."* The v2 path is gated by `JOBSEARCH_ENABLE_CV_QUALITY_V2`, which is off by default.
- **Legacy path (v1).** `application-pack.v1` has no document files, only a rendered Markdown projection.
- **6C.** Enrolled applications are prepared autonomously up to a system-confirmed pack (v1) or `NEEDS_USER(document_selection_required)` (v2). Inbox, notifications, dossier and derived state are in place.
- **6B.** `approved_answers` is versioned by `supersedes_id`, with provenance `USER` | `USER_EDITED_PROPOSAL`, basis and reach. `proposed_answers` (`SYSTEM_PROPOSED`) can't be used until approved. `RepresentationRequirement`s come with `AnswerCandidate`s. The subject policy covers freshness, sensitivity and reach. `apply_target_confirmations` and the `ProvenanceTier` values include `user_confirmed_apply_target`. The immutable, content-hashed `fill-manifest.v1` has sources `EVIDENCE` | `APPROVED_ANSWER` | `PACK_DOCUMENT`, a closed transform set and `value_hash`. Grants bind pack, manifest hash, answers, apply target, identity and policy hash. `request_grant` and `pre_click_commit` exist.
- **Phase 3 handoff.** The extension fills safe fields for a human, and JobSearch never clicks the employer's submit. `submission_confirmations` records the user's own statement.

## 4. Concepts

- **Reviewable application.** The complete, derived view of one application that the user reviews (§6). It is a pure function of current state.
- **Approval binding.** The canonical document (§9.1) computed from the reviewable application, containing exactly what approval covers. `binding_hash = canonical_hash("application-approval-binding", "v1", binding)` uses 6B's canonical hashing.
- **Approval.** An immutable record that the user approved one binding for FILL (§9).
- **Review delta.** A new or changed item that wasn't part of the approved binding, discovered later, typically by 6D-B filling (§11). It returns the application to `NEEDS_REVIEW` for just that item.
- **Displayed binding hash.** The binding hash the review page rendered. Every approving request must carry it (§9.3).

## 5. Review states and transitions

Review state is **derived** (like 6B/6C lifecycle state). It is never stored as mutable authority.

| State | Derived when |
|---|---|
| `NOT_READY` | No current confirmable application yet (6C still preparing, stopped for a human/operational reason before a pack exists, or no job/target). |
| `READY_FOR_REVIEW` | A reviewable application exists and no approval has ever been recorded for this application. |
| `NEEDS_REVIEW` | A previous approval exists but no longer matches the current binding (it was invalidated or revoked, or it expired), **or** open review deltas exist. Carries every reason. |
| `APPROVED_FOR_FILL` | The latest approval is not revoked or expired, its `binding_hash` equals the current binding hash, and no review deltas are open. |
| `CLOSED` | The workflow status is past `drafted` (`applied`, …). Review no longer applies and history is kept. |

Later bundles derive further states *on top of* `APPROVED_FOR_FILL` (6D-B `FILLING`/`FILLED_AWAITING_SUBMISSION`; 6E-A `SUBMISSION_AUTHORIZED`/`SUBMITTED`). Each of them requires `APPROVED_FOR_FILL` to still hold at the moment it acts.

```text
                 prepared (6C) / user builds pack
NOT_READY ─────────────────────────────────────────▶ READY_FOR_REVIEW
                                                          │ approve (binding hash = displayed hash)
                                                          ▼
       ┌──────────── material change / delta / expiry / revoke ─── APPROVED_FOR_FILL
       ▼                                                          ▲
  NEEDS_REVIEW ── user reviews changes/deltas, approves again ────┘
       │
  any state ── workflow moves past drafted ──▶ CLOSED
```

**Blocking issues.** `READY_FOR_REVIEW` and `NEEDS_REVIEW` list *blocking issues* that make the Approve action unavailable. They are:
- a planned answer with no approved value;
- an unaccepted AI proposal;
- a required sensitive subject that isn't answered for this application;
- no apply target;
- no exact document files (Decision D1);
- an unacknowledged ATTENTION warning;
- an identity conflict.

## 6. The reviewable application (what the user sees)

One page per application ("Prepared Applications" → application). Everything on it that affects what would be sent is part of the binding (§9.1).

1. **Job:** title, employer, location, the job posting snapshot identity (content id), strong job identity key, and a link to the dossier (6C).
2. **Where it will be sent:** the apply target's canonical URL and its provenance tier, in plain words ("verified from discovery" / "you confirmed this exact URL" / "you supplied it; filling only").
3. **Documents:** the CV and cover letter as the employer will receive them. For each one:
   - a preview (§7.1);
   - the exact filename, size and SHA-256;
   - its origin ("AI-generated from your reviewed evidence" / "Your document, not content-verified by JobSearch");
   - the actions **Download exact file**, **Replace with revised file** and (Decision D3) **Edit content**.
4. **Planned answers:** every answer JobSearch expects to give (§8), each showing:
   - the question or subject;
   - the value as it will be entered;
   - its source and provenance label (§8.3);
   - its reach and freshness.
   
   Missing or proposed answers are highlighted as blocking.
5. **Claims and provenance:** for AI-generated documents, each claim is listed with its label (Profile evidence / AI-derived / User supplied) and a link to the profile evidence it came from (§8.3). User-uploaded documents are labelled as a whole ("user-managed").
6. **Warnings** (§6.1).
7. **Fit summary:** informational only and **not** part of the binding (fit changes don't alter what is sent).
8. **Actions:** **Save changes**, **Approve for filling** and **Revoke approval**. There is no submit action anywhere in 6D (§12).

### 6.1 Warnings

Warnings are derived with a stable `warning_key` (type + subject + fingerprint).

- **BLOCKING:** prevents approval. Examples:
  - missing required answer;
  - an unaccepted AI proposal;
  - a stale document basis (the approved source changed);
  - an expired answer needed for this application;
  - an identity conflict;
  - no apply target;
  - no exact files.
- **ATTENTION:** approval requires an explicit acknowledgement, and acknowledged keys enter the binding. Examples:
  - AI-derived (inferred) claims present;
  - FLAG/UNVERIFIED gates the user resolved;
  - a user-managed document not content-verified;
  - an apply target supplied by the user (filling only, not a submit-capable target);
  - an answer expiring within its freshness window;
  - a newer AI draft being available (§7.4).
- **INFO:** shown only. Examples: fit score, 6C preparation notes.

A new ATTENTION warning appearing after approval changes the acknowledgement set, so the binding changes and the approval is invalidated.

## 7. Documents

### 7.1 Preview

- **DOCX** (the only upload format today) gets an in-app, read-only rendering of document structure and text, produced server-side from the stored bytes. The server never trusts a client-side conversion. The page states that the preview is a rendering, and that the employer receives the exact file with the SHA-256 shown. **Download exact file** always serves the exact stored bytes.
- **PDF** (if the upload scope is ever widened) is shown natively in the browser from the exact bytes.
- The preview is never used to *derive* anything that is sent. It's for human inspection only.

### 7.2 Versions

Document versions stay immutable (the v2 model). Replacing a file uploads a new `user_uploaded` version and moves the selection pointer to it, which is an explicit user action that increments `revision`. Old versions are kept and listed in history.

### 7.3 Edit and replace

- **Replace with revised file** reuses the v2 upload contract as-is (validation, content addressing, filename handling).
- **Edit content** (Decision D3) edits the structured text of an AI-generated document (CV statements / cover-letter paragraphs). The edit is stored as a user-owned content revision and rendered by the existing renderer into a new document version with origin `user_edited`, a new enum value that the migration adds. The rendered file is what gets selected and approved.

### 7.4 User-owned content is never silently overwritten (I-4)

- **P1.** The selection pointer changes only by explicit user action. Neither autonomy nor any pipeline rerun ever moves it.
- **P2.** `user_uploaded` / `user_edited` versions are immutable. Regeneration creates *new* AI versions and never replaces or deselects a user version. When a newer AI draft exists after upstream changes, the review shows the ATTENTION warning "a newer AI draft is available; your version is kept", with **Compare** and an explicit **Use the new draft** action.
- **P3.** Content-unit edits (D3) are user-owned. A later regeneration never merges into them. The user must explicitly choose to discard their edit.
- **P4.** Answers: a USER / USER_EDITED_PROPOSAL approved answer is superseded only by another user action. `SYSTEM_PROPOSED` proposals never supersede or alter an approved answer.

## 8. Planned answers

### 8.1 The planned answer set

The set holds the answers JobSearch expects to give for this application. It is the union of:
- (a) the 6B representation requirements for this application (governing questions from job understanding and blocker subjects), each resolved through its approved-answer candidates exactly as the 6B context does;
- (b) identity/contact fields sourced from profile evidence (name, email, phone, location), as `EVIDENCE` entries;
- (c) resolved review deltas (§11).

Each entry has:
- `answer_key` (the stable requirement key);
- `subject`, `required`, the display question;
- `source_kind` (`EVIDENCE` | `APPROVED_ANSWER`), `source_ref` (evidence id or approved-answer id);
- `value_hash` (6B `value_hash`) and `display_value`;
- `permitted_transforms` (from 6B's closed transform set);
- `provenance_label`, reach and freshness.

### 8.2 Editing answers

Editing or answering creates a new `approved_answers` row (USER, `supersedes_id` set) through the existing 6B answer path, with the user choosing the reach up to the subject's maximum. Accepting a system proposal creates `USER_EDITED_PROPOSAL`. Sensitive required subjects (6B §7) are answered per application only, never as a standing answer. Free text is only ever a user-approved answer (6B decision 2).

### 8.3 Claim provenance labels

| Label | Meaning | Source |
|---|---|---|
| **Profile evidence** | Stated in your evidence profile | Content units / answers whose evidence ids are in the current bound profile snapshot; `EVIDENCE`-sourced answers |
| **AI-derived** | Inferred by JobSearch from your evidence (e.g. transferable or functionally equivalent match), with the evidence it was inferred from | Units tied to judgment review items; system proposals once the user accepts them are relabelled |
| **User supplied** | You wrote or approved this | USER / USER_EDITED_PROPOSAL answers; `user_edited` / `user_uploaded` documents |

Labels are derived from recorded sources and never from wording. A label the system can't derive shows **Unknown source**, which is a BLOCKING warning for AI-generated content.

## 9. Approval

### 9.1 The approval binding (exact contents)

```json
{
  "schema_version": "application-approval-binding.v1",
  "account_id": "...", "application_workspace_id": "...",
  "job": {"identity_key": "...", "identity_strength": "SOURCE_RECORD|CANONICAL_URL", "job_posting_content_id": "..."},
  "apply_target": {"canonical_url": "...", "provenance": "discovery_verified|user_confirmed_apply_target|user_supplied|..."},
  "pack": {"artifact_id": "...", "content_hash": "sha256:...", "schema_version": "application-pack.v2"},
  "documents": [{"kind": "cv|cover_letter", "document_version_id": "...", "sha256": "...", "byte_length": 0, "origin": "..."}],
  "answers": [{"answer_key": "...", "subject": "...", "source_kind": "EVIDENCE|APPROVED_ANSWER", "source_ref": "...", "value_hash": "...", "permitted_transforms": ["..."]}],
  "acknowledged_warnings": ["warning_key", "..."],
  "review_contract_version": "review-contract.v1"
}
```

All lists are sorted canonically. Fields deliberately **excluded** (so they never invalidate): standing policy, capability settings, budgets, limits, kill switch, pause, fit score, 6C notes. Those govern *authority* and are re-checked by 6B at every stage (I-2).

### 9.2 The approval transaction

All of the following happens in one `BEGIN IMMEDIATE` transaction:

1. Check ownership, that the workflow status isn't past `drafted`, and that the kill switch and pause are clear. Approving while halted is refused, because approval would enable later automation.
2. Compute the current reviewable application and binding. The approval is refused if there are blocking issues, or if the request's `displayed_binding_hash ≠ current binding_hash` (409 *"this application changed since you reviewed it"*).
3. If the current selections aren't yet bound into the current v2 final pack, perform the v2 Gate 4 confirmation of exactly those selection revisions inside the same transaction (the user's own Gate 4). Then recompute and re-check the binding.
4. Insert `application_approvals` (§14) with `scope = 'FILL'`, the binding JSON and hash, `supersedes_id` (the previous approval), `batch_id` (bulk) and actor, and append an `APPROVED` review event.
5. Resolve the application's open review deltas that this binding now covers. Wake the application's 6C queue item (wake-only).

### 9.3 Stale-view protection

The review page renders the binding hash it displayed. Every approve (single or bulk) sends it back, and the server recomputes. Any difference refuses the approval for that application, so no approval can cover content the page didn't show (I-1).

### 9.4 Revocation and expiry

- **Revoke approval** is always available and appends `REVOKED`, which gives `NEEDS_REVIEW(revoked)`.
- Approvals expire after `approval_ttl` (Decision D4, default 14 days), which gives `NEEDS_REVIEW(expired)`.

## 10. Bulk review and approval

- The Prepared Applications list offers **Approve selected (N)**. There is never an "approve all" or "submit all".
- An application is eligible for bulk approval only if the user has **opened its full review page at its current binding hash**: a `REVIEW_OPENED` event carrying that hash (Decision D5). The list shows which selected items are ineligible and why.
- The request carries, per application, the displayed binding hash from the review the user opened. Each application goes through §9.2 **independently**, with one approval record each and a shared `batch_id` for audit. A refusal for one application doesn't affect the others. The response reports each outcome.

## 11. Review deltas (contract that 6D-B consumes)

When a later stage (6D-B filling, or a re-ingested job) finds something that isn't in the approved binding, it registers a **review delta**. 6D-A provides the intake service and API. It never discovers deltas itself.

**Delta kinds:**
- a new required or optional question (unclassified or classified subject);
- a changed question for an approved `answer_key`;
- a new upload requirement (for example a third document);
- a declaration or attestation;
- an apply-target change (redirect outside the approved target, different tenant);
- a value that fails its permitted transforms.

**Rules:**
- **R1.** An open delta makes the application `NEEDS_REVIEW` immediately, and any in-flight 6D-B session must stop before its next write. This is enforced by 6D-B through the binding re-check.
- **R2.** The review page shows *only* the deltas, alongside a compact summary of what was already approved and hasn't changed.
- **R3.** Resolving a delta means answering or accepting it, which extends the answer set. The new approval (§9.2) is a **complete** binding, not a patch. It supersedes the prior approval, and its record lists the deltas it resolved.
- **R4.** A delta for a required sensitive subject can only be answered for this application (never as a standing answer). Declarations and attestations always need explicit per-application answers.
- **R5.** Deltas are append-only records with status derived from resolution events.

## 12. The approval ≠ submission boundary (technical guarantees)

- **G1. Representation.** `application_approvals.scope` has `CHECK (scope = 'FILL')`. A submission approval can't be stored by 6D code.
- **G2. Separate authority.** 6E-A will introduce `submission_authorizations` (one-time, per application, bound to `binding_hash` + policy/control version + target). From 6D-A on, `request_grant(stage=SUBMIT)` refuses unless a valid submission authorization exists (Decision D7). No such record can exist before 6E-A, so SUBMIT grants are impossible, regardless of capability ceilings.
- **G3. Structural.** 6D modules never import or call `pre_click_commit` or `request_grant` with `SUBMIT`. The structural test in the 6C style is extended to these modules.
- **G4. Interfaces.** A FILL grant (6D-B) will require a valid approval whose binding covers every fill-manifest entry: document entries match approved sha256, answer entries match approved `(answer_key, value_hash, transform ∈ permitted_transforms)`, and evidence entries match approved evidence refs. No SUBMIT interface accepts an approval.
- **G5. UI.** 6D has no "Submit" control. The primary action is **Approve for filling**, with copy stating that filling doesn't submit and that submission will ask separately.

## 13. Audit and history

Every event is an append-only row with actor, time and `seq`:
- `REVIEW_OPENED` (with the binding hash);
- `DOCUMENT_REPLACED` / `DOCUMENT_EDITED` / `SELECTION_CHANGED`;
- `ANSWER_EDITED` / `PROPOSAL_ACCEPTED`;
- `WARNING_ACKNOWLEDGED`;
- `APPROVED`;
- `APPROVAL_INVALIDATED` (reason list and the old vs new binding hashes);
- `REVOKED`, `EXPIRED`;
- `DELTA_OPENED`, `DELTA_RESOLVED`.

Invalidation is *derived*: validity is always "the hash still matches". `APPROVAL_INVALIDATED` rows are also recorded, idempotently, the first time any reader or the sweep observes a mismatch, so the history shows when and why. The dossier (6C) gains an **Approvals** section covering bindings, diffs between successive bindings, deltas and who did what.

## 14. Data model (migration `019_review_approval`)

- **`application_approvals`** (append-only): `seq`, `id`, `account_id`, `application_workspace_id`, `scope` CHECK = 'FILL', `binding_json`, `binding_hash`, `supersedes_id`, `batch_id`, `resolved_delta_ids_json`, `actor`, `created_at`.
- **`application_review_events`** (append-only): `seq`, `id`, `account_id`, `application_workspace_id`, `event`, `binding_hash`, `detail_json`, `actor`, `created_at`.
- **`review_deltas`** (append-only): `seq`, `id`, `application_workspace_id`, `kind`, `answer_key`, `subject`, `observed_json`, `source` (e.g. `FILL_SESSION:<id>`), `created_at`. Resolution is recorded in `application_review_events`.
- **Document content revisions** (D3 only): `document_content_revisions` (append-only structured text edits) and the `user_edited` origin value.
- **Triggers:** append-only triggers on all of the above (the 6C pattern). No mutable authority columns.

## 15. Interaction with 6B and 6C (additive only)

- **6C.**
  - Scheduling, steps and outcomes are unchanged.
  - The PREPARED inbox entry and notification link to the review page and read "Ready for review".
  - A v2 `NEEDS_USER(document_selection_required)` stop is resolved on the review page.
  - Approval wakes the 6C queue item (wake-only, as all resolution paths do).
- **6B.**
  - The authorization engine is unchanged.
  - The one code-level change is G2's SUBMIT refusal (a restriction that can only reduce).
  - FILL grant issuance consuming approvals is 6D-B's change.
- **Legacy v1.** v1 applications can be reviewed (pack content, answers, warnings) but can't reach `APPROVED_FOR_FILL`: "exact document files required" is a blocking issue (Decision D1).

## 16. API and UI surface

**API:**
- `GET /api/applications/prepared` returns the list, with derived review state, blocking/attention counts and eligibility for bulk.
- `GET /api/workspaces/{id}/review` returns the reviewable application plus the binding hash. It records `REVIEW_OPENED`.
- `GET /api/workspaces/{id}/review/documents/{kind}/preview` returns a rendered preview. The exact-bytes download stays the existing v2 route.
- `POST .../review/documents/{kind}` handles replace (the v2 upload) and select.
- `POST .../review/answers` handles answer or accept-proposal (6B path).
- `POST .../review/warnings/ack` acknowledges a warning.
- `POST .../review/approve` takes `{displayed_binding_hash, acknowledged_warnings}`.
- `POST .../review/revoke` revokes an approval.
- `POST /api/applications/approve-selected` takes `{items: [{workspace_id, displayed_binding_hash}]}`.
- `POST /api/workspaces/{id}/review/deltas` is the internal intake for 6D-B.

**UI:** a Prepared Applications page (nav item) and the per-application review page (§6). Both use server-rendered templates in the existing style.

## 17. Decisions for review

- **D1 — Exact files required for approval.** `APPROVED_FOR_FILL` requires the v2 exact-file final pack. While `JOBSEARCH_ENABLE_CV_QUALITY_V2` is off, applications can be reviewed but not approved for filling. *Recommended* (consistent with "the human owns the final documents" and with exact-hash binding). The alternative, generating files from v1, would put unreviewed rendered bytes into the chain.
- **D2 — No PDF conversion in 6D-A.** Preview is an in-app rendering plus an exact-bytes download. If employer forms require PDF, conversion (and its dependency) is decided in 6D-B, and the converted file then becomes its own reviewed document version.
- **D3 — In-app content editing.** It is included as the last phase (7), behind the same preview/approval rules, and could be deferred without affecting the rest. Replace-with-file covers editing in Word from day one.
- **D4 — Approval TTL.** Default 14 days (operator setting, lower-only).
- **D5 — Bulk eligibility.** Bulk requires the full review page to have been opened at the current binding hash.
- **D6 — Warnings.** Warnings are BLOCKING / ATTENTION / INFO, and ATTENTION acknowledgements are bound into the approval.
- **D7 — SUBMIT refusal now.** 6D-A adds the SUBMIT refusal to 6B `request_grant` (G2), so the boundary is enforced by code before 6E exists.
- **D8 — 6C wording and links.** PREPARED becomes "Ready for review" and links to the review page. There is no behaviour change.

## 18. Acceptance criteria

1. The review page shows job, target, both documents (preview, exact hash, origin), every planned answer with source and provenance label, and warnings. Every element that affects what is sent is in the binding (property test: changing any bound element changes the hash; changing any excluded element does not).
2. Approving with a stale `displayed_binding_hash` is refused and writes nothing. Approving with blocking issues is refused.
3. A successful approval writes exactly one approval record and one `APPROVED` event. With v2, it binds a Gate-4-confirmed pack with the exact selection revisions.
4. Each of these, after approval, derives `NEEDS_REVIEW` with the right reason and records `APPROVAL_INVALIDATED` once:
   - replacing a document, changing a selection, or editing content;
   - editing, superseding or expiring an answer;
   - a change to the apply target URL or provenance;
   - a job posting or identity change;
   - a new ATTENTION warning;
   - a review delta;
   - revocation;
   - TTL expiry.
   
   Changing policy, capability, budget or pause **doesn't** invalidate the approval.
5. Re-approval after a delta shows only the deltas, and produces a complete new binding that supersedes the old one and lists the resolved deltas.
6. Bulk: N selected → N independent outcomes and N approval records with one `batch_id`. Ineligible items (not opened at the current hash, or with blocking issues) are refused individually.
7. User-owned content:
   - a pipeline rerun or 6C activity never changes a selection or a user answer;
   - a newer AI draft appears only as an ATTENTION warning with an explicit **Use the new draft**.
8. Approval ≠ submission:
   - the `scope` CHECK rejects anything but FILL;
   - `request_grant(SUBMIT)` is refused with no submission authorization;
   - the structural test passes;
   - no "Submit" control is rendered.
9. v1 applications show "exact document files required" as a blocking issue and can't be approved.
10. Audit: every action in §13 appears in order (by `seq`) in the review history and the dossier Approvals section.
