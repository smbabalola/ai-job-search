## 1. Purpose and the core invariant

The default JobSearch workflow is now:

```text
PREPARE  →  REVIEW  →  FILL  →  SUBMIT
(6C)        (6D-A)     (6D-B)    (6E-A; 6E-B optional)
```

6D-A defines the **human review and approval contract** that every later automation step relies on. Everything else in Bundle 6D/6E consumes this contract; nothing may bypass it.

> **Core invariant (I-1): No action beyond what the user actually reviewed may inherit the user's approval.**

Concretely, an approval is a record of *one exact application*, identified by a content hash over everything the user was shown (§9). The approval stays valid only while the current state still recomputes to exactly the same hash. There's no "mostly the same" and no manual refresh. Anything the user didn't see is by definition not approved.

Supporting invariants:

- **I-2 Approval is not authority.** An approval records the user's consent to the *content and target*. Authority (capability, standing policy, budgets, limits, kill switch, pause) stays with 6B and is evaluated separately and freshly. Both are required for FILL. Neither alone is enough. So human review, editing and approval stay available while automation is paused or the kill switch is engaged. Pause and kill switch block later automated FILL grants and execution, never a human reviewing their own application. A user can prepare their queue while automation is stopped and resume it deliberately later.
- **I-7 Approval never creates what it approves.** An application is approvable only when an immutable final pack already exists for the exact current document selections (§7.2). The approve action records consent to that existing binding. It never creates, confirms or changes the pack.
- **I-8 Filling is mechanical.** Every known application field is bound to either an exact approved answer or an explicit `OMIT` disposition (§8.4). A later filler enters exactly what was approved or leaves exactly what was approved blank. It never decides on its own.
- **I-3 Approval for filling never grants submission.** 6D approvals cannot represent submission consent (§12). Submission authority is a separate, one-time, per-application record introduced in 6E-A.
- **I-4 The user owns what they edited.** User-supplied or user-edited content is never silently replaced, merged or regenerated by the AI (§7.4).
- **I-5 One application, one approval record.** Bulk actions create one independent approval record per application (§10).
- **I-6 History is append-only.** Every approval, edit, invalidation, revocation and re-approval is an immutable event (§13). Current state is derived by `seq`, never by timestamp.

## 2. Scope and bundle separation

| Bundle | Owns | Explicitly does not |
|---|---|---|
| **6D-A — Review & Approval** (this spec) | Prepared Applications review UI; document preview/replace/edit; planned-answer review and editing; claim provenance; warnings; the approval record and its binding; invalidation; bulk approval; review deltas (intake contract); audit history; the approval-≠-submission boundary | Open employer sites, fill forms, drive a browser, click anything, submit |
| **6D-B — FILL** | Filling an *approved* application on the employer site behind a technical submit firewall; registering newly discovered fields as review deltas (§11) | Activate the employer's final submit control; fill anything outside the approved binding |
| **6E-A — User-authorized SUBMIT** | "Submit application": a one-time, per-application submission authorization bound to the same binding hash plus policy/control version; the pre-click transaction | Submit without that authorization |
| **6E-B — Optional autonomous SUBMIT** | An explicitly enabled higher-trust mode (off by default, deliberate activation, strong warning) | Become the default; weaken 6B limits, pause, kill switch or audit |

Operating modes (account setting, introduced for real in 6E-B, named here so the contract is stable): **Prepare only** → **Review before submit** (default) → **Autonomous submit**. 6D-A implements the review surface and approval records. Modes other than the default are not selectable in 6D.

**Non-goals for 6D-A:**
- browser automation or extension changes;
- fill manifests produced from live pages;
- PDF conversion (Decision D2);
- an in-app word processor, and in-app structured content editing (Decision D3: deferred to a separable follow-on);
- changes to 6C scheduling behaviour (§15);
- any path to `applied`.

## 3. Verified baseline (`master@fc316ee`)

What 6D-A builds on, unchanged:

- **Final documents (CV Quality v2).** Documents are immutable `application_document_versions` (`origin` `ai_generated` | `user_uploaded`, `sha256`, `byte_length`, content-addressed blob store). A single `application_document_selections` pointer per kind carries an explicit `revision`, and `reusable_application_documents` holds documents saved for reuse. v2 Gate 4 (`_confirm_application_pack_v2`) binds exact selection revisions into an immutable `application-pack.v2` artifact. Its `final_documents[kind]` carries the version id, sha256, byte length, origin and filename. The governing principle is *"AI creates the documents. The human owns the final documents."* The v2 path is gated by `JOBSEARCH_ENABLE_CV_QUALITY_V2`, which is off by default.
- **Legacy path (v1).** `application-pack.v1` has no document files, only a rendered Markdown projection.
- **6C.** Enrolled applications are prepared autonomously up to a system-confirmed pack (v1) or `NEEDS_USER(document_selection_required)` (v2). Inbox, notifications, dossier and derived state are in place.
- **6B.** `approved_answers` is versioned by `supersedes_id`, with provenance `USER` | `USER_EDITED_PROPOSAL`, basis and reach. `proposed_answers` (`SYSTEM_PROPOSED`) can't be used until approved. `RepresentationRequirement`s come with `AnswerCandidate`s. The subject policy covers freshness, sensitivity and reach. `apply_target_confirmations` and the `ProvenanceTier` values include `user_confirmed_apply_target`. The immutable, content-hashed `fill-manifest.v1` has sources `EVIDENCE` | `APPROVED_ANSWER` | `PACK_DOCUMENT`, a closed transform set and `value_hash`. Grants bind pack, manifest hash, answers, apply target, identity and policy hash. `request_grant` and `pre_click_commit` exist.
- **Phase 3 handoff.** The extension fills safe fields for a human, and JobSearch never clicks the employer's submit. `submission_confirmations` records the user's own statement.

## 4. Concepts

- **Reviewable application.** The complete, derived view of one application that the user reviews (§6). It is a pure function of current state.
- **Approval binding.** The canonical document (§9.1) computed from the reviewable application, containing exactly what approval covers. `binding_hash = canonical_hash("application-approval-binding", "v1", binding)` uses 6B's canonical hashing.
- **Approval.** An immutable record that the user approved one binding for FILL (§9).
- **Review delta.** A new or changed item that wasn't part of the approved binding, discovered later, typically by 6D-B filling (§11). It returns the application to `NEEDS_REVIEW` for just that item.
- **Displayed binding hash.** The binding hash the review page rendered. Every approving request must carry it (§9.3).

## 5. Review states and transitions

Review state is **derived** (like 6B/6C lifecycle state). It is never stored as mutable authority.

| State | Derived when |
|---|---|
| `NOT_READY` | No current confirmable application yet (6C still preparing, stopped for a human/operational reason before a pack exists, or no job/target). |
| `READY_FOR_REVIEW` | A reviewable application exists and no approval has ever been recorded for this application. |
| `NEEDS_REVIEW` | A previous approval exists but no longer matches the current binding (it was invalidated or revoked, or it expired), **or** open review deltas exist. Carries every reason. |
| `APPROVED_FOR_FILL` | `approval_effective` holds (see below). |
| `CLOSED` | The workflow status is past `drafted` (`applied`, …). Review no longer applies and history is kept. |

Two predicates are kept distinct, and code must never treat the first as permission:

- **`binding_matches`**: the latest approval's `binding_hash` equals the current binding hash. The content, target, fields and material warning state are unchanged.
- **`approval_effective`**: all of the following hold:
  - `binding_matches`;
  - no current blocking issue;
  - no unacknowledged ATTENTION warning;
  - no open review delta;
  - the approval isn't revoked;
  - the approval isn't past its TTL.

`APPROVED_FOR_FILL` is exactly `approval_effective`. 6D-B and 6E must check `approval_effective`, never hash equality alone.

Later bundles derive further states *on top of* `APPROVED_FOR_FILL` (6D-B `FILLING`/`FILLED_AWAITING_SUBMISSION`; 6E-A `SUBMISSION_AUTHORIZED`/`SUBMITTED`). Each of them requires `APPROVED_FOR_FILL` to still hold at the moment it acts.

```text
                 prepared (6C) / user builds pack
NOT_READY ─────────────────────────────────────────▶ READY_FOR_REVIEW
                                                          │ approve (binding hash = displayed hash)
                                                          ▼
       ┌──────────── material change / delta / expiry / revoke ─── APPROVED_FOR_FILL
       ▼                                                          ▲
  NEEDS_REVIEW ── user reviews changes/deltas, approves again ────┘
       │
  any state ── workflow moves past drafted ──▶ CLOSED
```

**Blocking issues.** `READY_FOR_REVIEW` and `NEEDS_REVIEW` list *blocking issues* that make the Approve action unavailable. They are:
- no immutable final pack for the exact current document-selection revisions (§7.2);
- a required field with no approved answer (required fields can't be `OMIT`);
- an optional field with neither an approved answer nor an explicit `OMIT` disposition;
- an unaccepted AI proposal;
- a required sensitive subject that isn't answered for this application;
- no apply target;
- no exact document files (Decision D1);
- an unacknowledged ATTENTION warning;
- an identity conflict.

## 6. The reviewable application (what the user sees)

One page per application ("Prepared Applications" → application). Everything on it that affects what would be sent is part of the binding (§9.1).

1. **Job:** title, employer, location, the job posting snapshot identity (content id), strong job identity key, and a link to the dossier (6C).
2. **Where it will be sent:** the apply target's canonical URL and its provenance tier, in plain words ("verified from discovery" / "you confirmed this exact URL" / "you supplied it; filling only").
3. **Documents:** the CV and cover letter as the employer will receive them. For each one:
   - a preview (§7.1);
   - the exact filename, size and SHA-256;
   - its origin ("AI-generated from your reviewed evidence" / "Your document, not content-verified by JobSearch");
   - the actions **Download exact file** and **Replace with revised file** (edit it in Word or another editor, then upload it). In-app editing is deferred (D3).
4. **Planned fields:** every known application field JobSearch expects (§8), each showing:
   - the question or subject, and whether it is required;
   - its disposition: the value as it will be entered, or **Leave blank** (`OMIT`, optional fields only);
   - for answers, the source and provenance label (§8.3), reach and freshness.
   
   Required fields without an answer, optional fields without a disposition, and unaccepted proposals are highlighted as blocking.
5. **Claims and provenance:** for AI-generated documents, each claim is listed with its label (Profile evidence / AI-derived / User supplied) and a link to the profile evidence it came from (§8.3). This claim provenance is bound into the approval (§9.1). User-uploaded documents are labelled as a whole ("user-managed").
6. **Warnings** (§6.1).
7. **Fit summary:** informational only and **not** part of the binding (fit changes don't alter what is sent).
8. **Actions:** **Save changes**, **Approve for filling** and **Revoke approval**. There is no submit action anywhere in 6D (§12).

### 6.1 Warnings

Warnings are derived with a stable `warning_key` (type + subject + fingerprint).

- **BLOCKING:** prevents approval. Examples:
  - missing required answer;
  - an unaccepted AI proposal;
  - a stale document basis (the approved source changed);
  - an expired answer needed for this application;
  - an identity conflict;
  - no apply target;
  - no exact files.
- **ATTENTION:** approval requires an explicit acknowledgement (a separate action, §16). Examples:
  - AI-derived (inferred) claims present;
  - FLAG/UNVERIFIED gates the user resolved;
  - a user-managed document not content-verified;
  - an apply target supplied by the user (filling only, not a submit-capable target);
  - an answer expiring within its freshness window;
  - a newer AI draft being available (§7.4).
- **INFO:** shown only. Examples: fit score, 6C preparation notes.

**Warnings are bound as material state.** The binding carries every BLOCKING and ATTENTION warning as `(warning_key, level, acknowledged)`. INFO warnings stay outside it. So:
- a new ATTENTION or BLOCKING warning changes the binding immediately, even though nobody has acknowledged it;
- an answer expiring or becoming stale changes the binding immediately, through the warning it raises, even though the value hash is unchanged;
- acknowledging an ATTENTION warning changes the binding again, to a state the user can then approve.

Acknowledgement is always its own explicit action. The page re-renders with the new binding hash, and approval never acknowledges anything implicitly.

## 7. Documents

### 7.1 Preview

- **DOCX** (the only upload format today) gets an in-app, read-only rendering of document structure and text, produced server-side from the stored bytes. The server never trusts a client-side conversion. The page states that the preview is a rendering, and that the employer receives the exact file with the SHA-256 shown. **Download exact file** always serves the exact stored bytes.
- **PDF** (if the upload scope is ever widened) is shown natively in the browser from the exact bytes.
- The preview is never used to *derive* anything that is sent. It's for human inspection only.

### 7.2 Versions and the pack that gets approved

Document versions stay immutable (the v2 model). Replacing a file uploads a new `user_uploaded` version and moves the selection pointer to it, which is an explicit user action that increments `revision`. Old versions are kept and listed in history.

**Pack before approval (I-7).** Selecting or replacing a document is completed by **Save changes**. That is the user's own v2 confirmation of the exact current selection revisions (`_confirm_application_pack_v2`, the existing user Gate 4). It produces a new immutable `application-pack.v2` artifact, and the review page is then re-rendered with the new binding and its hash. The page is approvable only when the current pack's selection revisions equal the current selection pointers. Otherwise the blocking issue "save your document changes" is shown and there is no binding hash to approve. The approve action never calls Gate 4 and never writes a pack, so `displayed_binding_hash == current_binding_hash` always means "the user saw exactly this pack".

### 7.3 Replace (edit externally)

The initial 6D-A delivery is **preview → download → edit externally → replace → Save changes → review → approve**.

**Replace with revised file** reuses the v2 upload contract as-is (validation, content addressing, filename handling).

**In-app structured content editing (D3) is deferred** to a separable follow-on (a final phase or a small follow-on PR). When it lands, an edit becomes a user-owned content revision rendered into a new document version (origin `user_edited`). It follows the same pack-before-approval, binding and ownership rules, and nothing in the core depends on it.

### 7.4 User-owned content is never silently overwritten (I-4)

- **P1.** The selection pointer changes only by explicit user action. Neither autonomy nor any pipeline rerun ever moves it.
- **P2.** `user_uploaded` / `user_edited` versions are immutable. Regeneration creates *new* AI versions and never replaces or deselects a user version. When a newer AI draft exists after upstream changes, the review shows the ATTENTION warning "a newer AI draft is available; your version is kept", with **Compare** and an explicit **Use the new draft** action.
- **P3.** (With the D3 follow-on) content-unit edits are user-owned. A later regeneration never merges into them. The user must explicitly choose to discard their edit.
- **P4.** Answers: a USER / USER_EDITED_PROPOSAL approved answer is superseded only by another user action. `SYSTEM_PROPOSED` proposals never supersede or alter an approved answer.

## 8. Planned answers

### 8.1 The planned answer set

The set holds the answers JobSearch expects to give for this application. It is the union of:
- (a) the 6B representation requirements for this application (governing questions from job understanding and blocker subjects), each resolved through its approved-answer candidates exactly as the 6B context does;
- (b) identity/contact fields sourced from profile evidence (name, email, phone, location), as `EVIDENCE` entries;
- (c) **field** review deltas (§11), open or resolved, under their effective key (§11). Non-field deltas (documents, target) never become fields.

Each entry has:
- `answer_key` (the stable requirement key);
- `subject`, `required`, the display question;
- `disposition`: `ANSWER` or `OMIT` (§8.4);
- for `ANSWER`:
  - `source_kind` (`EVIDENCE` | `APPROVED_ANSWER`) and `source_ref` (evidence id or approved-answer id);
  - `value_hash` (6B `value_hash`) and `display_value`;
  - `permitted_transforms` (from 6B's closed transform set);
  - `provenance_label`, reach and freshness.

### 8.2 Editing answers

Editing or answering creates a new `approved_answers` row (USER, `supersedes_id` set) through the existing 6B answer path, with the user choosing the reach up to the subject's maximum. Accepting a system proposal creates `USER_EDITED_PROPOSAL`. Sensitive required subjects (6B §7) are answered per application only, never as a standing answer. Free text is only ever a user-approved answer (6B decision 2).

### 8.3 Claim provenance labels

| Label | Meaning | Source |
|---|---|---|
| **Profile evidence** | Stated in your evidence profile | Content units / answers whose evidence ids are in the current bound profile snapshot; `EVIDENCE`-sourced answers |
| **AI-derived** | Inferred by JobSearch from your evidence (e.g. transferable or functionally equivalent match), with the evidence it was inferred from | Units tied to judgment review items; system proposals once the user accepts them are relabelled |
| **User supplied** | You wrote or approved this | USER / USER_EDITED_PROPOSAL answers; `user_edited` / `user_uploaded` documents |

Labels are derived from recorded sources and never from wording. A label the system can't derive shows **Unknown source**, which is a BLOCKING warning for AI-generated content.

### 8.4 Answer or leave blank: every known field has a disposition

- Every known field in the planned set carries exactly one disposition: `ANSWER` (bound to the exact approved answer or evidence value) or `OMIT` (leave blank).
- `OMIT` is an explicit per-application user choice, recorded as an append-only disposition event. It is allowed only for optional fields. A required field can't be omitted, and an unanswered required field is BLOCKING.
- An optional field with no disposition is BLOCKING ("answer it or choose Leave blank"). The system never defaults an optional field to either outcome.
- If 6D-B later finds that a field bound as `OMIT` (optional) is actually mandatory, or finds any field that isn't in the planned set, that is a review delta (§11).
- A filler must enter exactly the bound `ANSWER`, or leave an `OMIT` field untouched. It never chooses between them.
- An **unclassified** field delta (no supported semantic subject) can't receive an answer, because approved answers require a known subject. If it's required, it stays BLOCKING until it's classified to a supported subject (§11 R7). If it's optional, its only valid disposition is `OMIT`.

## 9. Approval

### 9.1 The approval binding (exact contents)

```json
{
  "schema_version": "application-approval-binding.v1",
  "account_id": "...", "application_workspace_id": "...",
  "job": {"identity_key": "...", "identity_strength": "SOURCE_RECORD|CANONICAL_URL", "job_posting_content_id": "..."},
  "apply_target": {"canonical_url": "...", "provenance": "discovery_verified|user_confirmed_apply_target|user_supplied|..."},
  "pack": {"artifact_id": "...", "content_hash": "sha256:...", "schema_version": "application-pack.v2"},
  "documents": [{"kind": "cv|cover_letter", "document_version_id": "...", "sha256": "...", "byte_length": 0, "origin": "...",
                 "claim_provenance_hash": "sha256:... (ai_generated only; null for user-managed)"}],
  "fields": [{"answer_key": "...", "subject": "...", "required": true, "disposition": "ANSWER|OMIT",
              "source_kind": "EVIDENCE|APPROVED_ANSWER|null", "source_ref": "...|null", "value_hash": "...|null",
              "permitted_transforms": ["..."]}],
  "review_warnings": [{"warning_key": "...", "level": "BLOCKING|ATTENTION", "acknowledged": false}],
  "review_contract_version": "review-contract.v1"
}
```

All lists are sorted canonically. The pack referenced must already exist for the exact current selection revisions (I-7).

**Claim provenance digest.** For each AI-generated document, `claim_provenance_hash = canonical_hash("claim-provenance", "v1", [...])` covers every claim shown beside it:
- the claim or unit id and its claim content hash;
- its provenance classification (Profile evidence / AI-derived / User supplied);
- for each cited evidence item (sorted by reference), both its `evidence_ref` and its immutable `evidence_basis_hash` (the hash of that evidence's content or basis as presented).

The user reviews what the evidence says, not just which identifier it has. Binding the content hash keeps the contract safe even if evidence storage ever allows content to change under a stable id. If the evidence or provenance presented to the user changes, the approval is invalidated even when the document bytes are identical. User-managed documents carry `null` and keep the document-level "not content-verified" ATTENTION warning.

**Component hashes.** The binding hash is computed over the whole document, and the server also derives one component hash per section: `job`, `apply_target`, `pack`, one per document, one per field (by `answer_key`), and `review_warnings`. They're used to show exactly which sections changed (§11.1, §13).

Fields deliberately **excluded** (so they never invalidate): standing policy, capability settings, budgets, limits, kill switch, pause, fit score, 6C notes. Those govern *authority* and are re-checked by 6B at every stage (I-2).

### 9.2 The approval transaction

All of the following happens in one `BEGIN IMMEDIATE` transaction:

1. Check ownership and that the workflow status isn't past `drafted`. Pause and kill switch are **not** checked. Approval is consent, not authority (I-2), and those controls block later FILL grants and execution instead.
2. Compute the current reviewable application and binding. The approval is refused, writing nothing, when:
   - there is no immutable pack for the exact current selection revisions (I-7);
   - there are blocking issues;
   - the request's `displayed_binding_hash ≠ current binding_hash` (409 *"this application changed since you reviewed it"*).
3. Insert `application_approvals` (§14) with `scope = 'FILL'`, the binding JSON and hash, `supersedes_id` (the previous approval), `batch_id` (bulk) and actor, and append an `APPROVED` review event. No pack, document, selection or answer is written by this transaction.
4. If this approval resolves open review deltas, write exactly one `DELTA_RESOLVED` event per resolved delta. Wake the application's 6C queue item (wake-only, which is harmless while paused or halted).

**Write contract.**
- A normal approval writes one `application_approvals` row and one `APPROVED` event, plus the queue wake.
- A re-approval that resolves deltas additionally writes exactly one `DELTA_RESOLVED` event per resolved delta.
- Approval never writes packs, documents, selections, answers, dispositions, warning acknowledgements or any other application content.

The request carries only `displayed_binding_hash`.

### 9.3 Stale-view protection

The review page renders the binding hash it displayed. Every approve (single or bulk) sends it back, and the server recomputes. Any difference refuses the approval for that application, so no approval can cover content the page didn't show (I-1).

### 9.4 Revocation and expiry

- **Revoke approval** is always available and appends `REVOKED`, which gives `NEEDS_REVIEW(revoked)`.
- Approvals expire after `approval_ttl` (Decision D4, default 14 days), which gives `NEEDS_REVIEW(expired)`.

## 10. Bulk review and approval

- The Prepared Applications list offers **Approve selected (N)**. There is never an "approve all" or "submit all".
- An application is eligible for bulk approval only if its full human-facing review page has been **presented at its current binding hash**: a `REVIEW_PRESENTED` event carrying that hash (Decision D5). `REVIEW_PRESENTED` is recorded only by the server-rendered review page route when it renders the full review. It is never recorded by the data API, prefetches or background processes. The list shows which selected items are ineligible and why.
- The request carries, per application, the displayed binding hash from the review page that was presented. Each application goes through §9.2 **independently**, with one approval record each and a shared `batch_id` for audit. A refusal for one application doesn't affect the others. The response reports each outcome.

## 11. Review deltas (contract that 6D-B consumes)

When a later stage (6D-B filling, or a re-ingested job) finds something that isn't in the approved binding, it registers a **review delta**. 6D-A provides the intake service and API. It never discovers deltas itself.

**Delta kinds:**
- a new required or optional question (unclassified or classified subject);
- a changed question for an approved `answer_key`;
- a new upload requirement (for example a third document);
- a declaration or attestation;
- an apply-target change (redirect outside the approved target, different tenant);
- a value that fails its permitted transforms.

**Field and non-field deltas.**
- **Field deltas** concern one field: a new or changed question, a declaration or attestation, a value that fails its transforms, and an `OMIT` field found to be mandatory.
- **Non-field deltas** concern a document or the target: a new upload requirement, a document conversion, and an apply-target change. They never become fields.
- **Effective key:** a delta's stored `answer_key`, or `delta:<delta_id>` when it has none. One canonical helper computes it everywhere.

**Rules:**
- **R1.** An open delta makes the application `NEEDS_REVIEW` immediately, and any in-flight 6D-B session must stop before its next write. This is enforced by 6D-B through the binding re-check.
- **R2.** A delta-only review is permitted only when it is proven (§11.1). The page then shows the deltas, and states that everything else is unchanged from the previous approval, with that approval's hash. Otherwise, every section whose component changed is shown in full, alongside the deltas.
- **R3.** Resolution is kind-specific. The new approval (§9.2) is always a **complete** binding, not a patch. It supersedes the prior approval, and its record lists the deltas it resolved, computed by per-kind resolution predicates:
  - A **field delta** extends the field set under its effective key. It's resolved by an approval whose binding decides that field (`ANSWER`, or `OMIT` where allowed). A transform-failure delta additionally needs a value hash different from the failing one, or `OMIT`.
  - A **non-field delta** is resolved only by an approval whose corresponding bound component satisfies it:
    - a target delta, when the bound apply target is the observed new target;
    - a conversion delta, when the bound document of that kind is a saved version in the required format;
    - a new-upload delta, when the binding contains a document of the required kind.

    Until then it stays open, and the application stays `NEEDS_REVIEW`.
- **R4.** A delta for a required sensitive subject can only be answered for this application (never as a standing answer). Declarations and attestations always need explicit per-application answers.
- **R5.** Deltas are append-only records with status derived from resolution events.
- **R6.** An `OMIT` field later found to be mandatory is always a delta. Its only valid resolutions are an answer, or abandoning the application.
- **R7.** An unclassified required question stays blocking until it's classified to a supported semantic subject. 6D-B supplies the classification, as a new delta carrying the subject for the same observed field. An unclassified optional question may only be omitted. No synthetic subject is ever invented.

### 11.1 Proving "everything else is unchanged"

Let `P` be the previous approved binding and `C` the current binding. A review is **delta-only** exactly when:
- every component present in `P` is still present in `C`: no component disappears, including a delta field;
- every component hash of `C` equals the same component in `P`, **except** fields whose effective key belongs to an open or just-resolved **field** delta, which may be added or changed; and
- no **non-field** delta is open or just resolved. A document or target delta always shows the affected sections in full.

Any other difference (document, claim provenance, target, job, pack, another field, review warnings) means it isn't delta-only. The page then shows those sections in full, marked as changed.

This check is a pure function over recorded bindings (`delta_only(P, C, delta_keys) -> bool`, plus the changed components). The user is told something is unchanged only when the hashes prove it.

## 12. The approval ≠ submission boundary (technical guarantees)

- **G1. Representation.** `application_approvals.scope` has `CHECK (scope = 'FILL')`. A submission approval can't be stored by 6D code.
- **G2. SUBMIT hard refusal.** From 6D-A on, `request_grant(stage=SUBMIT)` and the SUBMIT pre-click path refuse **unconditionally** (a fixed denial reason `submission_not_available`), regardless of capability ceilings, policy or settings. 6D-A introduces no placeholder submission-authorization model. 6E-A later replaces this hard refusal with validation of its real `submission_authorizations` (one-time, per application, bound to `binding_hash`, policy/control version and target). Before the guard is added, a regression test pins the existing Phase 3 human extension handoff flow (pairing, session, fill, `user_confirmed_submitted`) so the guard provably doesn't affect it.
- **G3. Structural.** 6D modules never import or call `pre_click_commit` or `request_grant` with `SUBMIT`. The structural test in the 6C style is extended to these modules.
- **G4. Interfaces.** A FILL grant (6D-B) will require a valid approval whose binding covers every fill-manifest entry:
  - document entries match the approved sha256;
  - answer entries match an approved `ANSWER` field `(answer_key, value_hash, transform ∈ permitted_transforms)`;
  - evidence entries match approved evidence refs;
  - no manifest entry writes to a field bound `OMIT`.
  
  No SUBMIT interface accepts an approval.
- **G5. UI.** 6D has no "Submit" control. The primary action is **Approve for filling**, with copy stating that filling doesn't submit and that submission will ask separately.

## 13. Audit and history

Every event is an append-only row with actor, time and `seq`:
- `REVIEW_PRESENTED` (with the binding hash; recorded only by the human-facing review page);
- `DOCUMENT_REPLACED` / `DOCUMENT_EDITED` / `SELECTION_CHANGED`;
- `PACK_CONFIRMED` (Save changes produced a new immutable pack);
- `ANSWER_EDITED` / `PROPOSAL_ACCEPTED` / `FIELD_DISPOSITION_SET` (`ANSWER` | `OMIT`);
- `WARNING_ACKNOWLEDGED`;
- `APPROVED`;
- `APPROVAL_INVALIDATED` (reason list and the old vs new binding hashes);
- `REVOKED`, `EXPIRED`;
- `DELTA_OPENED`, `DELTA_RESOLVED`.

Invalidation is *derived*: validity is always `approval_effective` (§5). One audit rule covers every cause:
- The first time any reader or the sweep observes that the latest approval is not effective, `APPROVAL_INVALIDATED` is recorded once for that approval and that exact set of reasons.
- The reasons are `binding_changed` (with the changed component names, §9.1), `open_deltas`, `revoked`, `expired`, `blocking_issues` and `unacknowledged_attention`.
- A later, different reason set records a new `APPROVAL_INVALIDATED`.
- Revocation also has its own `REVOKED` event (the user action), and expiry its own `EXPIRED` event. The dossier (6C) gains an **Approvals** section covering bindings, diffs between successive bindings, deltas and who did what.

## 14. Data model (migration `019_review_approval`)

- **`application_approvals`** (append-only): `seq`, `id`, `account_id`, `application_workspace_id`, `scope` CHECK = 'FILL', `binding_json`, `binding_hash`, `supersedes_id`, `batch_id`, `resolved_delta_ids_json`, `actor`, `created_at`.

The current disposition is by `seq`. `ANSWER` fields bind their approved-answer or evidence source. `OMIT` is refused by the service for required fields.

## 15. Interaction with 6B and 6C (additive only)

- **6C.**
  - Scheduling, steps and outcomes are unchanged.
  - The PREPARED inbox entry and notification link to the review page and read "Ready for review".
  - A v2 `NEEDS_USER(document_selection_required)` stop is resolved on the review page.
  - Approval wakes the 6C queue item (wake-only, as all resolution paths do).
- **6B.**

## 16. API and UI surface

**API:**
- `GET /api/applications/prepared` returns the list, with derived review state, blocking/attention counts and eligibility for bulk.
- `GET /api/workspaces/{id}/review` returns the reviewable application plus the binding hash. It is **read-only** and records nothing.
- `GET /workspaces/{id}/review` is the human-facing review page (server-rendered HTML). Rendering the full review records `REVIEW_PRESENTED(binding_hash)`, which is the only evidence D5 accepts.
- `GET /api/workspaces/{id}/review/documents/{kind}/preview` returns a rendered preview. The exact-bytes download stays the existing v2 route.
- `POST .../review/documents/{kind}` handles replace (the v2 upload) and select.
- `POST .../review/save` is **Save changes**: the user's v2 confirmation of the exact current selection revisions, producing the immutable pack. The page re-renders with the new binding hash.
- `POST .../review/answers` handles answer or accept-proposal (6B path).
- `POST .../review/fields/{answer_key}/disposition` sets `ANSWER` or `OMIT` (optional fields only).
- `POST .../review/warnings/ack` acknowledges a warning.
- `POST .../review/approve` takes `{displayed_binding_hash}` only. It never acknowledges warnings (acknowledgement is its own action above).
- `POST .../review/revoke` revokes an approval.
- `POST /api/applications/approve-selected` takes `{items: [{workspace_id, displayed_binding_hash}]}`.
- `POST /api/workspaces/{id}/review/deltas` is the internal intake for 6D-B.

**UI:** a Prepared Applications page (nav item) and the per-application review page (§6). Both use server-rendered templates in the existing style.

## 17. Decisions (resolved at review, 2026-09-26)

- **D1 — Exact files required: approved.** `APPROVED_FOR_FILL` requires the v2 exact-file final pack and its hashes. There is no legacy-v1 fallback. The feature flag stays during development, but **6D-A isn't deployably usable while CV-v2 is disabled**. Enabling the exact-file path is an explicit rollout requirement for 6D-A.
- **D2 — No PDF conversion in 6D-A: approved.** If 6D-B finds that an employer requires PDF:
  - conversion creates a **new document version** and opens a non-field `DOCUMENT_CONVERSION` delta (§11 R3). The delta is resolved only when that converted version is selected, saved into the pack and re-approved;
  - the application returns to `NEEDS_REVIEW`;
  - the converted PDF can't be filled or uploaded until it has been reviewed and re-approved.
- **D3 — In-app content editing: deferred from the core.** The initial delivery is preview → download → edit externally → replace → Save changes → review → approve. Structured in-app editing is a separable follow-on and doesn't delay the approval boundary.
- **D4 — Approval TTL 14 days: approved.** It can be configured shorter, never silently longer. Expiry removes permission to fill. It deletes no approval or history.
- **D5 — Bulk eligibility: approved.** Each application's full review page must have been presented at its current binding (`REVIEW_PRESENTED`; never granted by a data API GET). The action is `Approve selected (N)`, never "Approve all".
- **D6 — BLOCKING / ATTENTION / INFO: approved.** The material warning state (every BLOCKING and ATTENTION warning, with its acknowledgement) is bound into the approval. INFO is not.
- **D7 — SUBMIT impossible now: approved with adjustment.** An unconditional hard refusal with no placeholder authorization model (G2), which 6E-A replaces. The existing human extension flow is regression-tested before the guard is added.
- **D8 — "Ready for review": approved.** The wording and link only, with no 6C behaviour change.

## 18. Acceptance criteria

1. **Binding coverage.** The review page shows job, target, both documents (preview, exact hash, origin), claim provenance for AI documents, every planned field with its disposition (and for answers, source and provenance label), and warnings. Every element that affects what is sent or what is presented as its basis is in the binding. Property test: changing any bound element changes the hash, and changing any excluded element (policy, capability, budget, limits, pause, kill switch, fit score) does not.
2. **Refusals write nothing.** An approval is refused, with nothing written, when:
   - the `displayed_binding_hash` is stale;
   - there are blocking issues;
   - there is no immutable pack for the exact current selection revisions.
3. **Approval's write contract (I-7).** Tested with a DB diff around the approve call:
   - a normal approval writes exactly one approval row and one `APPROVED` event, plus the 6C queue wake;
   - a delta re-approval additionally writes exactly one `DELTA_RESOLVED` event per resolved delta;
   - no approval writes a pack, document, selection, answer, disposition or warning acknowledgement;
   - an approve request never acknowledges a warning. With an unacknowledged ATTENTION warning, approval is refused.
4. **Pack before approval.** Changing a selection without Save changes makes the page non-approvable. Save changes creates exactly one immutable v2 pack for the exact revisions, and the re-rendered binding hash is the one that can be approved.
5. **Invalidation.** Each of these, after approval, derives `NEEDS_REVIEW` with the changed component(s) as the reason, and records `APPROVAL_INVALIDATED` once:
   - replacing a document or changing a selection (followed by Save);
   - a claim-provenance change with byte-identical documents;
   - editing, superseding or expiring an answer;
   - changing a field disposition;
   - a change to the apply target URL or provenance;
   - a job posting or identity change;
   - a new ATTENTION or BLOCKING warning, including one raised by an answer expiring or becoming stale with an unchanged value hash;
   - a review delta;
   - revocation;
   - TTL expiry.
   
   Changing policy, capability, budget or pause, or engaging the kill switch, **doesn't** invalidate the approval.
6. **Approval while automation is stopped.** With automation paused or the kill switch engaged, review, edit, Save changes and approve all succeed. No FILL grant or execution is possible (6B refuses; 6D-B honours it).
7. **Delta-only re-approval (§11.1).**
   - When only delta fields differ from the previous approval, the page shows only the deltas plus "everything else unchanged" with the previous hash.
   - When any other component differs (a document, claim provenance, target, job, another field, review warnings), that section is shown in full and marked as changed.
   - Property test: `delta_only` is true exactly when all non-delta component hashes are equal, no component of `P` disappears, and no non-field delta is involved.
   - A `TARGET_CHANGE`, `NEW_UPLOAD` or `DOCUMENT_CONVERSION` delta always gives the full view of the affected sections, and resolves only per R3.
   
   Re-approval produces a complete superseding binding that lists the resolved deltas.
8. **Answer or leave blank.**
   - A required field without an answer blocks approval, and `OMIT` on a required field is refused.
   - An optional field without a disposition blocks approval.
   - `OMIT` is bound in the binding.
   - A delta intake for an `OMIT` field reported as mandatory opens a delta and gives `NEEDS_REVIEW`.
   - An unclassified required delta stays blocking and can't be answered. An unclassified optional delta accepts only `OMIT`.
9. **Bulk.** N selected give N independent outcomes and N approval records sharing one `batch_id`. Ineligible items (no `REVIEW_PRESENTED` at the current hash, blocking issues, or stale) are refused individually. A data API GET of the review never makes an item eligible.
10. **User-owned content.** A pipeline rerun or 6C activity never changes a selection, answer or disposition. A newer AI draft appears only as an ATTENTION warning with an explicit **Use the new draft**.
11. **Approval ≠ submission.**
    - The `scope` CHECK rejects anything but FILL.
    - `request_grant(SUBMIT)` and the SUBMIT pre-click path are refused unconditionally, even with a SUBMIT ceiling and policy.
    - The Phase 3 human extension handoff regression test passes before and after the guard.
    - The structural test passes, and no "Submit" control is rendered.
12. **Binding match vs effective approval.**
    - `APPROVED_FOR_FILL` holds only when `approval_effective` holds.
    - A test constructs each case where `binding_matches` is true but the approval isn't effective: a blocking issue, an unacknowledged ATTENTION warning, an open delta, revocation, TTL expiry. Each gives `NEEDS_REVIEW`.
13. **Claim provenance by content.** Changing a cited evidence item's content/basis hash, while its `evidence_ref` and the document bytes stay the same, changes `claim_provenance_hash` and invalidates the approval.
14. **Exact files.** v1 applications, and any application while CV-v2 is disabled, show "exact document files required" as a blocking issue and can't be approved.
15. **Audit.** Every action in §13 appears in order (by `seq`) in the review history and the dossier Approvals section.
16. **Concurrency.**
    - Two approvals of one application racing (same hash) give exactly one record; the other is a no-op or 409.
    - Approve racing Save changes gives either a refusal as stale, or an approval of the earlier pack that is immediately invalid. Never a partial state.
17. **No 6C regression.** 6C scheduling behaviour is unchanged. The existing 6B/6C suites pass unchanged, apart from the added SUBMIT-refusal tests.

## 19. Testing strategy

- **Pure:**
  - binding and component hashes, the claim-provenance digest, state derivation, warning derivation, provenance labelling, invalidation reasons, `delta_only`;
  - Hypothesis properties: hash sensitivity to bound fields (including BLOCKING/ATTENTION warning state) and insensitivity to excluded ones (INFO warnings included); claim-provenance sensitivity to evidence content at identical bytes and identical refs; `delta_only` iff the non-delta components are equal; derivation monotonicity (adding a delta or warning never yields a more permissive state); `approval_effective` implies `binding_matches`, never the reverse.
- **Services:** Save changes (pack creation), approval (stale, blocking, no pack, the write contract by DB diff including `DELTA_RESOLVED`), acknowledgement as its own action, `REVIEW_PRESENTED` only from the page route (not the data API), approve while paused or halted, revoke, expiry, dispositions, deltas, bulk, user-ownership rules, G2 refusal, and the human extension handoff regression.
- **Concurrency:** separate connections, WAL, run 20×.
- **Browser (Playwright, committed):** review page, preview, replace + Save, answer edit, Leave blank, approve, stale-view refusal, delta-only view, bulk, no submit control.
- **Migrations:** `019` fresh, plus upgrade from a pre-6D DB built by `master@fc316ee` code.
